# 浏览器单写者的持久化与恢复协议草案

状态：Proposed。对应设计草稿第 1 个评审问题。调研于 2026-11-11，整理于 2026-11-12，Asia/Taipei。

本文只提出协议，不改变工作台行为。模型、配置和实测结果见 [形式验证说明](formal/README.md#singlewriter-扩展模型)，动作及抽象边界见 [模型索引](formal/single-writer-notes.md)。

## 结论与适用边界

浏览器决定编辑语义和提交顺序。服务保存唯一的持久日志，并检查提交是否仍有写入权。服务可以重放日志，但不能自行修改作品。这两种职责不冲突，也不要求服务拥有第二份可独立编辑的作品。

首版每个项目只允许一个未确认的提交。笔画期间可以渲染预览。只有服务确认日志已持久保存后，工作台才发布已提交状态、更新正式撤销记录，并向 Agent 返回成功。可以先显示“预览中”或“等待保存”，不能先显示“已保存”。

这需要补充两个条件。

1. 写入权的世代号 `epoch` 必须先持久保存，再发给浏览器。服务重启不能把世代号归零。
2. 服务把“检查写入权、检查基础版本、追加日志、确认持久化”和“交接写入权”放在同一个项目串行队列里。只在收到请求时检查一次世代号不够。

不采用依赖时钟的租约到期正确性。心跳只帮助发现故障，显式接管才更换持有者并增加 `epoch`。浏览器冻结时，旧页面可能仍自认为是写入者。协议保证的是服务不会接受旧世代的新写入，不是让所有失联页面同时知道自己已失去权限。

## 各方持有什么

| 参与者 | 状态 | 是否在进程崩溃后保留 |
| --- | --- | --- |
| 浏览器标签页 | 当前视图、已知持久修订、预览、待确认操作、连接请求代次、获授世代号 | 否 |
| 浏览器本地待发记录 | 项目身份、原操作 ID、完整不可变负载、基础日志摘要、操作前后值 | 模型假设完成的本地事务保留。浏览器存储被清除或驱逐不在保证内 |
| 服务进程 | 连接、项目串行队列、正在写入的记录 | 否 |
| 服务磁盘 | 项目身份、日志、当前世代号、持有者、已处理的授予请求标识 | 是，前提是所选存储正确完成持久化 |
| 网络 | hello、sync、commit 和 ack 消息 | 不能依赖。消息可能迟到、丢失或因重试重复 |

操作日志是恢复真源。快照是可重建的加速缓存，不另存一份可独立覆盖日志的“当前作品”。日志记录必须包含操作 ID、作者、依赖版本、基础修订、前后值、结构版本及结果摘要。模型用可重放的整数增量代表完整操作记录，没有验证真正的豆格结构。

浏览器本地记录只帮助找回未确认的修改，不等于服务的持久成功。尚未完成的笔画预览可以在崩溃时丢失，界面不能把它标为已保存。

## 身份和消息

建议消息包含以下标识。

- `projectId` 标识协作项目，不能从文件名推断。导入同名 JSON 也不能自动继承原历史。
- `sessionId` 标识工作会话。`tabId` 和 `incarnationId` 区分页面实例及重新打开的实例。
- `acquireRequestId` 区分每次恢复或显式接管请求，服务持久去重。模型用每标签页单调递增的 `req` 同时抽象实例代次和请求代次，没有分别验证随机 UUID 的生成。
- `epoch` 是服务持久分配的写入权世代号。
- `opId` 是修改意图的身份。重试保留原 ID 和负载，不重新量化、不重新生成补偿、不换 ID。
- `baseRev`、`baseDigest` 和依赖版本标识该负载基于哪份状态。

服务首先检查身份。对于已提交的 `opId`，验证负载摘要相同后返回原持久结果。即使原世代已经过期，也可以返回既有操作的只读回执，但不能因此恢复写入权。相同 ID 携带不同负载时返回 `OP_ID_REUSE`。

只有未知 `opId` 才进入新提交路径，依次检查当前持有者、页面实例、世代号、基础版本和操作前提。模型把每个 ID 的负载设为不可变，尚未检验恶意 ID 复用。

## 正常提交顺序

1. 浏览器等待活动笔画结束。在同一个会话队列里重新检查读取依赖和结构版本。
2. 浏览器固定操作 ID、负载、基础修订及预期旧值。浏览器完成本地待发记录，再把完成的修改显示为等待保存。笔画绘制中的即时预览不必等待这一步。
3. 浏览器把携带当前世代号的提交发给服务。`WebSocket.send()` 返回、缓冲区归零、HTTP 入队回执都不能表示已保存。
4. 服务进入项目串行队列。先处理已知操作 ID，再验证新提交的身份、世代号和基础状态。模型采用整份日志前缀严格一致的保守校验。原设计的“无关区域可兼容”仍由浏览器依赖检查决定，不能把旧命令的 baseRev 原封不动交给服务强行覆盖。
5. 服务写入一条完整日志记录并等待持久化。世代交接不能插入这段区间。日志、操作 ID 及恢复所需历史是一个可重放记录，不能分别成功。
6. 服务返回包含 `projectId`、`opId`、结果修订和摘要的持久回执。
7. 浏览器只接收匹配当前请求代次、操作 ID 和世代的回执。浏览器发布已提交状态、显示“已保存至 rev N”，清理本地待发记录，然后处理下一项。Agent 的成功响应也到此才成立。

若回执先于页面发布而页面崩溃，日志重放恢复状态。若页面收到过成功又崩溃，服务仍能重建该操作。模型的历史观察变量 `everAcked` 不随页面崩溃清除，专门检查后一条。

## 恢复先核对身份，再核对日志，最后恢复编辑

页面重开、服务重启、连接重建以及 bfcache 恢复均进入同一路径。

1. 页面暂停正式提交，载入本地待发记录。页面提供项目、会话、页面实例、恢复请求 ID、已知修订和摘要。
2. 服务从磁盘恢复日志和写入权记录，校验完整记录边界。服务不能从文件名、WebSocket 连接先后或“第一个标签页”推定项目及写入者。
3. 用户已明确选择该页面继续编辑或显式接管时，服务在项目队列里持久增加世代号，记录持有者和授予请求 ID，再回复同步快照。重复授予请求返回原结果，旧请求不能再次接管。
4. 页面核对响应身份和请求 ID。迟到的旧恢复响应不得让新页面回退。仅比较修订数字不够，还要比较日志前缀或可信摘要。
5. 页面按下表处理。全部核对完成后才恢复正式编辑。未确认操作仍保留“等待保存”。

| 对账结果 | 处理 |
| --- | --- |
| 两端修订及日志摘要相同 | 无待确认操作则继续。已有操作 ID 出现在日志里，则取得原持久结果并去掉本地重复预览 |
| 服务较新，页面是日志前缀 | 重放缺少的日志。若待确认操作已在日志中，不再执行。页面硬崩溃后从空视图恢复也属于这一类 |
| 页面较新，且只多出可证明接在服务日志后的待发操作 | 用原操作 ID 和不可变负载，在新世代下重发。服务重新检查前提 |
| 同一修订但摘要不同，或两端分叉 | 阻断并保留待发负载，展示差异。不能自动取较大修订，也不能静默丢弃本地修改 |
| 页面较新但没有原操作记录 | 不能根据页面终值凭空重建历史。保留为恢复候选，由用户选择导出或重新计划 |
| 项目或会话身份不符 | 拒绝绑定。用户可以明确创建新协作项目，不自动连接旧历史 |

模型中的 `ReceiveSync` 采用完整日志序列比较，摘要碰撞不在模型里。模型遇到分叉进入 `blocked`，并保留 journal。它没有模拟用户解决分叉。

## 三个中断窗口

| 中断位置 | 服务可能保存什么 | 恢复顺序 |
| --- | --- | --- |
| 页面已应用，尚未发送 | 没有这条日志 | 从本地待发记录取得原 ID。握手后确认日志前缀，再重发。若连本地记录都未完成，只能说明该预览未保存 |
| 已发送，尚未确认持久化 | 可能没有，也可能已完成持久化但响应在路上 | 不能靠超时猜失败。先查询原 ID。存在则返回原结果，不存在且基础状态未变则重发。基础已变则阻断 |
| 已持久化，尚未收到回执 | 完整日志已在磁盘 | 服务重放或查询 ID 返回原回执。浏览器清除重复预览和待发记录，绝不再施加一次增量 |

中断后保留服务未写盘的队列没有帮助。服务进程重启会丢队列。关键是浏览器保留原请求身份，服务保留已提交身份，并在重新执行前对账。

## 只在接收时检查世代号仍然有漏洞

`SingleWriterGrantRace.cfg` 刻意允许写入权交接插入“接收校验”和“写盘”之间，同时删掉写盘前的重新检查。TLC 找到以下路径。

1. 标签页 A 获授 epoch 1 并生成操作。
2. 服务接收 A 的操作，检查 epoch 1 合法，尚未写盘。
3. 标签页 B 获授 epoch 2。
4. 服务把 A 的旧世代操作写盘。

修正后的正向协议把授予世代号和提交持久化放进同一个项目队列，`Grant` 要求 `work = None`。模型的 `Flush` 同时再次要求当前世代有效。这两条在模型内形成明确的顺序。

这不是现有工作台已实现的漏洞。它是协议候选的反例。最终正向配置没有发现安全性反例。建模中修复的记录类型和布尔赋值括号错误是模型编码错误，不应冒充产品协议缺陷。

## 浏览器生命周期不提供“最后一次保存”的保证

Chrome 的生命周期文档说明，hidden 或 frozen 页面可以直接被丢弃，不发任何事件。冻结暂停定时器和网络回调。不要把 `unload`、`pagehide` 或 WebSocket `close` 回调作为持久化前提。`visibilitychange` 可以帮助提前保存，但不能代替逐次提交的持久协议。[B1][B2]

bfcache 会保留整个 JavaScript 堆并暂停执行。`pageshow.persisted` 表示恢复了旧页面，不表示写入权仍有效。恢复时重新握手，期间禁止正式提交。Chrome 149 起还会在进入 bfcache 时关闭活动 WebSocket，因此“连接打开就一定阻止 bfcache”的旧经验已经不成立。[B2][B3]

WebSocket 标准把 `bufferedAmount` 定义为尚未发到网络的应用数据字节数。`send()` 及 `close()` 都没有服务应用层持久化语义。标准的 close 事件需要任务队列执行。页面被冻结或销毁时，不能假设脚本及时观察到服务已断线。[B4]

## Node 本地持久化可怎样落地

推荐先使用单一可重放日志作为真源，避免“项目文件写成功、历史文件写失败”的双文件事务。服务必须串行调用文件操作。Node 官方文档明确说明 `fs/promises` 并不自动同步多个并发修改。[D1]

若使用追加日志，每条记录包含长度、校验和、项目身份、修订及完整操作。服务循环处理短写，完成写入后调用 `FileHandle.sync()`，成功后才回执。启动扫描只接纳完整、可验证且连续的记录，并从日志重建去重索引。中间损坏要阻断，不能把已经回执过的后缀当垃圾删除。

检查点可以使用同目录临时文件，写完整内容后同步文件，再 rename 到目标，最后同步父目录。POSIX rename 保证名称替换的原子可见性，不单独保证断电后的持久性。Linux 文档要求另外同步父目录才能确保目录项也已落盘。[D2][D3]

创建新日志、轮转日志、替换世代号记录，也有目录项持久性要求。快照发布前不能删除仍用于恢复的日志。Windows、macOS、网络盘及真实硬件的写盘语义需要分别验收，不能把 Linux 方案原样宣称跨平台可靠。

Node 的 `writeFile({flush:true})` 会调用文件同步，但默认 `flush` 为 false。即使开启，也没有自动提供多文件事务、文件替换或父目录同步。[D1] 模型中的 `Flush` 是完整记录不可分割持久化的抽象，不是对这些系统调用的证明。

可选方案是使用具有明确事务和同步设置的嵌入式数据库。它仍要遵守相同的回执、世代号及恢复顺序，不能以“用了数据库”代替配置和故障测试。本次没有选择具体数据库。

## 验证边界

- `SingleWriter.cfg` 包含两个标签页、两个逻辑操作、最多两个世代、每标签页最多两次握手请求，浏览器崩溃总数及服务崩溃次数各最多两次。世代预算耗尽时允许停止恢复，不保证进展。
- `SingleWriterRestartTwice.cfg` 单独检查一个标签页、一个操作、三个世代、三次请求及两次完整浏览器重开周期，并包含服务两次崩溃。覆盖见证确认这些状态实际可达。
- 网络集合允许任意消息选择及丢弃。接收方可保留消息，等价于重复投递同一负载。它覆盖应用层跨重连乱序，比单条 WebSocket 的有序传输更弱。没有验证二进制帧解析、流量上限或重试退避。
- 浏览器 journal 在模型里是已完成事务且不被驱逐的稳定存储。IndexedDB 配额、事务中断、隐私模式、清理存储及跨设备恢复未验证。
- 服务磁盘记录原子性、校验算法、断电、坏扇区、目录同步和多个服务实例的进程锁均是外部假设。模型只有一个服务实例，不是共识协议。
- 新模型对新写入采用整份日志前缀校验。原模型继续覆盖局部依赖、结构失效及 ABA 撤销反例。两个模型没有组合证明，也没有验证任意尺寸、完整撤销栈、依赖图或颜色与完成标记联动。
- `ConvergenceAfterRecovery` 是有当前写入权且没有待确认操作时的一致性不变量，不是任意断网后都会恢复的保证。
- 另一个 `SingleWriterLive` 模型检查稳定环境中的最终对账。它假设之后没有新修改、接管、消息丢失及崩溃，并对发送、接收、重开、服务重启及写盘施加弱公平。它不保证永久断网、永久冻结、无限抢占或冲突自动解决。
- 本轮没有运行应用故障注入或 Playwright。尚未实现的协作功能不能接受这些端到端测试。下一轮验收清单见 [故障注入与浏览器验收清单](single-writer-recovery-tests.md)。
