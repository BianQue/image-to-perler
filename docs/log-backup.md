# 检查点之后收旧日志，以及恢复备份时避免分叉：协议验证

2026-11-12，Asia/Taipei。这是协议风险检查，不是应用功能实现，也不是保留多久或最多留多少条的产品政策。应用里还没有实现这些功能。

## 结论

日志仍是恢复真源。检查点只是可重建的加速缓存，不能另存一份可以单独覆盖日志的当前作品。压缩只能丢掉严格早于一份已经持久保存的检查点的前缀，不能靠改写或删除中间的人工记录来收拾历史。备份复制的是项目身份和当时可恢复的镜像，它不是第二条写入通道。

忧虑得到了证实。检查点还没写稳就删掉旧前缀，重放会丢掉已经提交的操作。未确认提交的基础前缀如果比将被丢掉的那段更短，压缩后就无法再核对这条仍有效的恢复路径。把一份更旧或对不上的备份直接写进正在使用的日志，会丢掉已经追加的后缀，或把现场日志改成另一条分叉历史。两条最短的错误恢复轨迹都命中了预期不变量（exit 12）：一条把较早的前缀 `<<1, 2>>` 写回已经走到 `<<1, 2, 3>>` 的现场日志；一条把分叉备份 `<<1, 9>>` 写进当时的 `<<1, 2>>`。损害发生在可恢复性和分叉，不是压缩拒绝本身。

好协议（关闭错误动作）在已检查的界限里守住了这些性质。主探索生成 65,994 个状态，7,653 个不同状态，深度 12，exit 0。检查点本身不删历史。检查点已经持久保存、且没有未确认提交仍依赖将被丢掉的前缀时，压缩之后用检查点加重放后缀，得到与压缩前相同的作品状态。备份与现场身份一致、且备份日志是现场可恢复日志的前缀时，恢复不改现场日志。身份不符、分叉，或备份带有无法证明属于同一条日志的额外后缀时，进入第 4 类硬停止，现场日志、世代号和未确认记录保持不变。压缩被拒绝不是第 4 类。

有两项产品选择本轮只标出，不选定默认策略。第一，压缩之后，只存在于被丢掉前缀里的操作还能不能做选择性撤销。第二，人是否可以明确选择「用这份备份整份替换现有协作项目」。禁止的是把对不上或更旧且并非前缀的备份静默写进同一条现场日志。

## 好协议的动作

状态里有一条只追加的逻辑历史、一份物理上仍保留的后缀、最多一份持久检查点和一份尚未落盘的待写入检查点、最多一条未确认提交，以及最多一份不可变备份。操作是按顺序编号的整数，作品状态是这条可恢复日志的重放结果。检查点保存当时前缀的可信摘要（这里直接保存前缀序列）和可重放快照。开始写一份新的检查点时，不得擦掉仍用于恢复的那份已经持久的检查点。

- `Checkpoint` 把当前可恢复前缀写成一份已经持久的检查点，不删日志。`StartCheckpoint` 只写入待落盘记录；`PersistCheckpoint` 把它变成持久检查点，同样不删日志。
- `Compact` 只有在检查点已经持久，并且未确认提交的基础前缀长度不短于将被丢掉的那一段时，才允许删掉该前缀。压缩后，`Replay(检查点, 剩余后缀)` 必须等于压缩前的作品状态。中间前缀的摘要并不单独保存，因此基础前缀更短的未确认提交仍依赖那段将被丢掉的日志。
- `Backup` 复制当前项目身份和可恢复镜像。备份是一份不可变快照，不会因为现场后来继续追加而自动改写。
- `RestoreMatching` 只在项目身份一致，并且备份日志是现场可恢复日志的前缀（含相等）时启用。这时恢复是空操作：备份已经被包含在现场日志里，不得把现场回退到更早的前缀。若备份比现场更长，即使现场看起来像它的前缀，本模型也不自动快进；那种情况要走硬停止，除非另有一次明确的身份或世代更换。
- `RejectRestore` 用于身份不符、分叉，或备份带有无法证明属于同一条日志的额外后缀。它把结果标成第 4 类，不改现场日志、世代号和未确认记录。

导出的 Project JSON 仍然不携带完整协作历史。日志里可能留着旧版本作品，那是之后要单独处理的隐私问题，不是本轮的不变量。模型里的长度上限只是为了让 TLC 能够穷举，不是保留政策。

## 检查了哪些性质

好协议（关闭全部错误动作和显式替换开关）要求以下不变量在界限内成立：

- `CheckpointDoesNotDelete`：写入检查点，或把待写入检查点落盘，都不改变物理日志、已丢掉的前缀长度和逻辑历史。
- `CompactPreservesState`：合法压缩后，检查点前缀加重放后缀等于压缩前的作品状态，逻辑日志也不变。
- `UnackedNotStranded`：若仍有未确认提交，则要么还没有丢掉前缀，要么它的基础前缀长度不少于已丢掉的长度，并且仍是当前可恢复日志的前缀。
- `RecoverableMatchesHist`、`NoFork`、`NoSilentLiveOverwrite`：可恢复日志始终等于只追加的逻辑历史，现场日志不会被静默覆盖或分叉。
- `RestoreRefusesSafely`、`UnackedPreservedOnReject`：硬停止的拒绝恢复不改现场日志、世代号、项目身份和未确认记录。
- `Class4OnlyOnHardStop`、`CompactNotClass4`：第 4 类只出现在拒绝恢复时。压缩、检查点和备份都不会把结果写成第 4 类。
- `HistAppendOnly`：除开放的显式替换外，逻辑历史只追加、不改写中间记录。
- `PrefixOpsNotSelectivelyUndoable`：合法压缩会留下 `prefix-selective-undo-left-open` 这条记录，用来标明「被丢掉前缀里的操作不再可做选择性撤销」只是模型里的保守记账，不是已经选定的产品默认。

`AllowCompactBeforeDurable`、`AllowCompactWithUnacked` 和 `AllowRestoreStaleOrDivergent` 只为反例打开。`AllowExplicitReplace` 只为开放选项的可达性见证打开；关闭时该动作不存在。

## 合法压缩，以及把旧备份写进现场日志的反例

`WitnessCompact`：先写入 `<<1, 2>>`，在修订 2 打下持久检查点，前缀是 `<<1, 2>>`，快照是 3。再追加操作 3，可恢复日志变成 `<<1, 2, 3>>`，重放状态是 6。随后合法压缩：物理日志变成 `<<3>>`，丢掉的前缀长度为 2，检查点仍是已经持久的那一份。用检查点前缀加后缀重放，仍得到 6，逻辑历史仍是 `<<1, 2, 3>>`。压缩本身不是第 4 类。模型在这条轨迹上记下 `prefix-selective-undo-left-open`，只表示被丢掉前缀里的操作在保守记账里不再可做选择性撤销，并没有把这一点定为产品默认。

对照之下，`NegativeCompactBeforeDurable` 在 `<<1, 2>>` 上只写下尚未持久的检查点，再追加操作 3 后压缩。待写入检查点不能作为恢复依据。物理日志变成 `<<3>>`，可恢复日志只剩下后缀，与完整历史 `<<1, 2, 3>>` 不一致。`NegativeCompactUnacked` 里，未确认提交的基础前缀是 `<<1>>`，短于修订为 2 的持久检查点；压缩仍然丢掉长度为 2 的前缀后，这条恢复路径无法再核对基础前缀。

`NegativeRestoreStale`：在 `<<1, 2>>` 上做备份，现场日志继续追加到 `<<1, 2, 3>>`。这份备份其实是现场日志的前缀，好协议应视为已经包含、不做回退。`RestoreStaleOrDivergent` 却把备份写进现场日志，物理日志变回 `<<1, 2>>`，已经追加的操作 3 从可恢复镜像里消失，并置起分叉标记。世代号仍是 1，说明这不是一次显式的身份或世代更换。

`NegativeRestoreDivergent` 更短：现场日志为 `<<1, 2>>`，导入的分叉备份为 `<<1, 9>>`。错误动作未做前缀核对，就把备份写进现场日志，物理日志变成 `<<1, 9>>`。对应的好协议轨迹 `WitnessRejectFork` 在同一份分叉备份上拒绝恢复，原因是 `fork`，第 4 类硬停止，现场日志仍是 `<<1, 2>>`。

`WitnessRestore` 表明，备份 `<<1, 2>>` 已是现场 `<<1, 2, 3>>` 的前缀时，匹配恢复不改现场。`WitnessCompactThenRestore` 还表明，压缩之后备份的是可恢复镜像 `<<1, 2, 3>>`，即使物理日志只剩下 `<<3>>`，匹配恢复也不改现场。

## 仍未决定的两项产品选择

1. 压缩之后，只存在于被丢掉前缀里的操作还能不能做选择性撤销。按当前前缀重推导补偿，依赖的就是这条可重放日志。前缀被丢掉之后，那些操作的原始记录不再在现场日志里。模型在合法压缩时记下这个问题，并采用「这些操作不再可做选择性撤销」作为保守的 v1 记账，但这不是已经选定的产品默认。

2. 人是否可以明确选择「用这份备份整份替换现有协作项目」。`WitnessExplicitReplace` 走到了这条受开关控制的路径：备份为 `<<1, 2>>`，现场已经追加到 `<<1, 2, 3>>`，并且还有一条未确认记录（id 4，基础前缀 `<<1, 2, 3>>`）。显式替换把世代从 1 增到 2，新历史变成 `<<1, 2>>`，旧日志没有合并进去，未确认记录仍保留、也没有被写进新历史。这不是第 4 类。开关关闭时，该动作不存在。本轮不把它定为产品默认。若将来允许替换，那也必须是一次显式的身份或世代更换，而不能在同一条日志上自动合并。

禁止的是把对不上、或更旧且并非现场前缀的备份静默写进正在使用的日志。

## 界限与未验证事项

这是有限界的穷举，不是任意长日志、任意图纸或真实磁盘的数学证明。主探索最多 3 条操作；定向路径把上限放到 4，以便安排「检查点、再追加、再压缩」以及「备份后现场继续走」这些路径。操作是按顺序编号的整数，作品状态是它们的重放和。模型没有检查真实的豆格结构、颜色或完成标记，也没有把选择性撤销的补偿算法重新展开一遍。

继承自单写入者工作、本轮也没有关闭的缺口仍然在：本模型没有重新展开单写入者的网络、崩溃、授予世代和恢复握手。它只检查检查点、压缩、备份和恢复这些动作，并沿用同一套项目身份、持久日志前缀、世代号、未确认记录，以及「服务日志是恢复真源」这条规则。服务磁盘记录的原子性、`fsync`、父目录同步、Windows 或网络盘的写盘语义，以及多个服务实例的进程锁，都是外部假设，不在本轮证明里。本轮没有重跑 SingleWriter、SelectiveUndo 与 PreviewAccept。

浏览器 journal 被清除、配额不够、隐私模式，以及跨设备恢复，都未验证。导出 JSON、备份目录怎么放、保留多久、怎么删，仍待评审。日志里旧版本作品的隐私问题，本轮没有写成不变量。应用功能还没有实现，因此也没有做故障注入或端到端验收。

相对路径复现命令见 [形式验证说明](formal/README.md#logbackup-扩展模型)。
